Materials internals¶

The user pages are Materials, Preview Surface, MaterialX surfaces, Opacity and glass and COP textures. This page records how hdUE implements them. The translation is src/hydra/materials.cpp (constants and textures into HdUEMaterialData) and the parent selection Scene.cpp in the backend (M_PreviewSurface, M_PreviewSurfaceMasked, M_PreviewSurfaceTranslucent, M_StandardSurface[Masked][Thin], M_StandardSurfaceTranslucent[Thin], each with a VT twin for virtual textures).

Prepared MaterialX¶

Prepared MaterialX rendering uses UE's editor-side Interchange importer to create native Substrate materials, followed by cook and staging. The runtime does not load USD or MaterialX importers. The usdview integration maps source materials to prepared native assets and applies supported public parameter edits.

.\scripts\Import-MaterialX.ps1 `
  -Source @('samples/materialx/standard_surface.mtlx','samples/materialx/open_pbr_surface.mtlx') `
  -OutputDirectory out/materialx-import/review
.\scripts\Stage-Runtime.ps1
.\scripts\Launch-Usdview.ps1 `
  -InputUsd samples/materialx/showcase.usda -CameraPath /Camera `
  -MaterialXLibrary out/materialx-import/review/library.json

Inline USD graphs use Import-UsdMaterialX.ps1 with samples/materialx/inline.usda and a fresh output directory. The supported subset includes Standard Surface, OpenPBR, color/vector/float images, float normal-map strength, UV0 coordinates, color/float multiplication, and float inversion. Nested NodeGraphs and interfaces are resolved during preparation. Cycles, unresolved images, incompatible connections and extra UV sets are rejected; displacement and volume outputs are exported with the surface. Imported materials are marked for instanced static meshes so they render on PointInstancer prototypes; that flag is set by the importer but has not been exercised on this branch.

Published scalar and color inputs can be edited without resending geometry. Structural or source-file changes require preparation, cook, staging, and restart. Dependency hashes detect stale registries. Texture overrides require prepared native texture paths.

The experimental Substrate Builder adds Houdini VOP authoring, typed USD graphs, and preparation into native UE Substrate materials. Texture Sample, UV Coordinates, Extract Channel, and Normal Map nodes connect images directly to Slabs and layer masks; explicit UDIM patterns use streaming virtual textures. Numeric/color inputs, UV transforms, channel selection, and normal controls update live through automatically generated material parameters. Node and wiring edits compile/cook in the background and replace the material in the same Houdini/UE process when ready. The earlier wet surface layer draft records the original fixed-profile proposal.

usdview and Solaris both accept the cooked registry through -MaterialXLibrary. In Solaris, the same file is the unreal:materialxLibrary render setting (hdUE Render Settings, Rendering > Materials > Cooked MaterialX Library), else the local runtime profile's materialx_library key. Preparation runs in Houdini's viewport; husk applies them as the viewport does: the delegate runs the same library code on the stage it renders (hdue_batch.py, through Houdini's Python) before each frame, and a material the library maps whose graph changed since its preparation fails the frame with the library's message instead of rendering a fallback. Bindings follow reference composition and validate the graph before applying native assets and parameters on the owner thread. A MaterialX material the library does not map renders through hdUE's own render-time translation, as with no library selected. Restart with a staged runtime containing the prepared materials; importing alone does not add them to an already running UE process.

Automatic import of untranslatable graphs¶

A MaterialX graph hdUE's render-time translation cannot express (a surface other than Standard Surface, OpenPBR or UsdPreviewSurface, or an input reached through a node outside its list: mix, place2d, noises, ramps, Houdini's own nodes, ...) is prepared through UE's MaterialX importer, as UE's USD importer translates MaterialX it finds in .mtlx files (MaterialXUSDShadeMaterialTranslator.cpp, Interchange). The live preparation that prepares Substrate Builder graphs does it, under the same render setting, Prepare Edited Materials (unreal:substrateAutoPrepare): the viewport keeps rendering the translation while UE's editor imports the graph in the background, then shows the imported material; husk prepares the graphs a frame needs before rendering it. Off, the graph renders translated, with the inputs it cannot translate at their constants. So does a graph whose preparation fails, in husk too: a machine without UE's editor and this repository's backend project (a package) cannot prepare, and prints why once. scripts/live_materials.py decides which graphs need it (usd_materialx_graph.needs_import, the node list of materials.cpp).

The graph is written as a MaterialX document (export_usd_materialx.py): MaterialX's standard nodes as they are, and Houdini's nodes (its library under houdini/materialx/libraries, node graphs over standard nodes) flattened into theirs, since UE reads only the standard libraries. A connected input's value is dropped: Houdini's generated node graphs carry both, which MaterialX 1.39's validation rejects. Every node graph UE does not translate whole (its CategoriesToSkip) is flattened too, then materialx_lowering.py rewrites what UE's importer reads differently or not at all (MaterialX 1.38 nodes, integers, matrices, flakes, primvar readers, and the graphs it fails or crashes on; the list is in Nodes UE imports). scripts/Test-MaterialXCoverage.ps1 -Export writes a document of every node Houdini ships, in chunks for Import-MaterialX.ps1. One editor imports it (HdUEImportMaterialX, the commandlet Import-MaterialX.ps1 runs) and cooks it with the job's other materials. Inputs the import keeps as material parameters (numeric and colour inputs of the graph's own nodes) stay live: editing them changes the material without a new import; values it bakes in (inside a flattened Houdini node, filenames, integer and boolean inputs) prepare the graph again. A prepared graph binds wherever it appears, at any path, and every later process on the runtime reuses it.

UE 5.8.4's place2d rotates by rotate/360 radians instead of rotate degrees: its MX_Place2D function scales the angle to turns for UE's Rotator, which reads radians (UMaterialExpressionRotator::Compile). HdUEImportMaterialX multiplies the input by 2π after the import, as it corrects UE's normal-map scale. samples/materialx/procedural.usda (place2d rotated 30 degrees, Houdini's checkers node, a mix) is the check: tests/husk_prepared_materials.py renders it translated and imported, and Launch-Houdini.ps1 -TestKind materialx-live -InputUsd samples\materialx\procedural.usda prepares an edit of it in the viewport.

Reference-safe MaterialX sample¶

Use samples/materialx/showcase_solaris.usda with Solaris Asset Reference. Its single default prim contains geometry, materials, lights, and cameras, and uses Y-up/meters. All 21 meshes retain bindings when referenced below another prim.

Each sample material references its material in the .mtlx document through USD's MaterialX file format (references = @standard_surface.mtlx@</MaterialX/Materials/SS_Glass>), so USD, Karma and hdUE's own translation all read the same graph; the cooked library maps the material by that document and material name. An older form, a Shader with info:mtlx:sourceAsset and a subIdentifier naming the material, still maps, but USD expects a nodedef name there and warns ("Invalid MaterialX NodeDef"). hdUE warns about a surface shader it cannot translate unless the library renders that material.

The original showcase.usda is a complete-stage sample. Its materials are outside the default geometry prim, so open it as a stage or sublayer. Referencing only the geometry prim drops its material bindings.

Regenerate the reference-safe scene through uv run with the configured Houdini Python executable and scripts/generate_solaris_materialx_sample.py.

Normal maps, UDIMs and texture memory¶

samples/materialx/normal_udim_showcase/normal_udim.usda contains synthetic color and normal UDIM fixtures. Prepare it with Import-UsdMaterialX.ps1 and a fresh output directory.

Normal maps use raw vector images through the float normal-map node. Import disables sRGB, uses normal compression, and adjusts the green channel for the UV convention. Strength scales decoded XY components before normalization. Custom tangent frames and vector-valued strength are unsupported.

UDIM validation covers conventional numbering, power-of-two resolutions, common aspect ratio, mixed resolutions, sparse tile sets, coordinates, and dependency hashes.

Live materials (UsdPreviewSurface, and the MaterialX graphs hdUE translates) read <UDIM> patterns at runtime, with no preparation: the backend builds UE's streaming virtual texture of the tiles it finds next to the pattern (VirtualTextureBuild.cpp), with UE's layout and choices (blocks placed for UE's flipped V, smaller tiles as mip-biased blocks, a mip tail block shared by all tiles, the project's r.VT.TileSize and r.VT.TileBorderSize). UE builds virtual textures only in the editor, so this is its builder's layout written again for the runtime. As the editor streams the chunks it builds from its virtual texture DDC cache files, hdUE writes each chunk once to its virtual texture cache, one file per chunk named by its hash, and UE's virtual texture system streams it from there through its file cache (Apply-ResidencyPatch.ps1): a set never stays in memory. A manifest per set, keyed by its tiles (path, time, size) and the build's choices, lets a reload skip decoding. The cache is %LOCALAPPDATA%\hdUE\VirtualTextureCache, or HDUE_VIRTUAL_TEXTURE_CACHE; it is never evicted (delete the folder, or use the Unreal menu, to reclaim space). Without a writable folder the chunks stay in memory, with a warning in the backend log. A material with a UDIM texture draws on the VT twin of its parent (M_PreviewSurfaceVT, ...), every texture of it virtual, as UE's USD import picks its VT reference material. Tiles that are not a power of two are stretched to one, where UE's import refuses them. Colour tiles in a colour space OCIO converts are converted one by one. The Path Tracer streams the pages its camera rays sample through UE's virtual texture feedback (PathTracingMaterialHitShader.usf): its first draws are a warm-up, with feedback from every pixel and UE's page upload throttle off, as Movie Render Queue's renders, and its accumulation restarts once the pages of the textures' physical pools stay the same for r.vt.FeedbackLatency + 2 draws, each after the GPU finished the one before. Locking every page of every mip instead, as hdUE did before, needed 2.1M pages on NVIDIA's Da Vinci Workshop against a pool of 7,224, and the Path Tracer never started. Surfaces seen only by secondary rays sample the pages that are resident, as in UE.

Live 2D textures are built at load, as UE's cooker builds them, and are not streamed: each is held whole, in memory until its upload and then on the GPU. The backend strips the top mips UE's cook would strip (TextureLODSettings.cpp, CalculateLODBias): the device profile's World texture group LODBias plus r.GlobalTextureLODBias, keeping at most the group's MaxLODSize (16384 by default). UE reads that variable when a texture is built, so set it at startup: HDUE_UE_ARGS=-DPCVars=r.GlobalTextureLODBias=1 halves every texture's width and height and holds a quarter of the memory. Virtual (UDIM) textures take the group's LODBias_VT instead, plus the same variable, up to MaxLODSize_VT, as UE cooks them: their tiles are halved as they load. With r.VT.EnableAutoImport (UE's "Enable virtual texture on texture import", off by default), a material with a texture of at least AutoVTSize x AutoVTSize texels (4096, UE's Texture Import setting; hdUE reads it from the engine ini, [/Script/TextureUtilitiesCommon.TextureImportSettings]) draws on the virtual parents too, as UE's texture import makes such textures virtual (TextureImportSettings.cpp, ShouldTextureBeVirtualByAutoImportSize), so its textures stream from the cache instead of staying whole on the GPU. The size comes from the image's header (PNG and JPEG; other formats stay 2D). The Da Vinci Workshop's materials read 2,100 UDIM sets (6,700 tiles, 62 gigapixels) and 1,280 other textures (15 GB block-compressed): with HDUE_UE_ARGS=-DPCVars=r.VT.EnableAutoImport=1 its husk render at full resolution peaks at 19 GB, where the textures alone held more than 40 GB in memory; the first load writes 41 GB of chunks.

The Path Tracer waits for all required streaming virtual-texture pages and mappings before accumulating. Planning and requests are spread across frames without synchronous file-I/O waits. Capacity limits and timeout fail rather than accumulating low-resolution images. The default pool is 128 MiB per physical format. Runtime UDIM sets are gated the same way. Adaptive virtual textures and automatic pool expansion are outside the current scope.

Cutout coverage mips¶

As UE's Interchange imports MaterialX: an image, or a constant below 1, is a cutout (masked) at UMaterial's default clip value 0.3333; a standard_surface with transmission is see-through instead (OpenPBR's geometry_opacity stays the cutout). The MaterialX spec, and Karma, render opacity as fractional coverage with no threshold, so moving a scene between them calls for material adjustments: Lumen reads the cutout from mipmaps, where thin foliage averages below the clip and would thin with distance. hdUE therefore scales the mips of every texture that drives a cutout (MaterialX opacity, UsdPreviewSurface with opacityThreshold) to keep its alpha coverage at the clip value, as UE's "scale mips for alpha coverage" texture setting does, with three fixes to UE's algorithm (ComputeAlphaScale in TextureCompressorModule.cpp): each level's scale is measured on that level rather than the previous one, the closest tested scale is kept rather than an untested midpoint, and a level is only ever scaled up. A 9x-distant thin-branch card keeps 0.42 of its near coverage (plain mips 0.05, UE's version less than plain); the Path Tracer reads the top mip and is unaffected

Layered Standard Surface parents¶

Materials with subsurface, sheen or a clear coat above 0 render with the layered Standard Surface parents: UE's own Substrate-StandardSurface-Opaque material function (the one UE's Interchange uses for MaterialX), fed the same texture slots, in four cooked variants (opaque or masked, solid or thin-walled; thin_walled is a static input of the function). Everything else, including standard_surface materials without subsurface, sheen or coat, uses the single-slab Preview Surface parents. The layered function mixes metal and dielectric slabs and layers coat and sheen vertically, so it costs several Substrate closures per pixel where Preview Surface costs one; keeping it to the materials that need it bounds that cost. In the Sponza gallery shot (960 x 540, Lumen, curtains covering about half the frame), the layered curtains cost about 1 to 2 ms per frame over the same curtains on Preview Surface (husk, 1500 realtime frames, measured twice).

COP texture export¶

The scene keeps its op: paths. Only Houdini can evaluate them, so the host exports each image the displayed stage's shaders and lights use to an EXR, outside LOP cooks, and passes the delegate the file for each path (hdue_set_viewport_textures in include/hdue/viewport_api.h); materials and lights then re-read their textures. Dirty and time-dependent outputs are checked on each host tick. Changed images receive immutable content-hash paths and reset Path Tracer accumulation. Unchanged images are reused. Cache files and the helper ROP are removed on shutdown. A path the host has not exported yet renders as untextured. husk does not evaluate op: paths (it has no node to cook): it renders them untextured with a warning naming each path, so save COP images to files for husk.

Glass profiles (usdview)¶

Optical glass uses a local profile that selects meshes and supplies IOR, roughness, attenuation color/distance, thickness, and coverage. Optical properties are not inferred from display opacity. Realtime refraction uses a thickness approximation; the Path Tracer follows geometry and absorption. Profiles and scene-specific generators stay local and ignored. usdview takes the profile with Launch-Usdview.ps1 -GlassProfile (scripts/glass_controls.py, /Game/HdUE/M_Glass); it applies to meshes on the displayColor fallback material.

Cooked native asset placement¶

In Houdini, Render Geometry Settings' Native Asset field (Unreal Engine tab) offers them as a menu: the levels, meshes, Blueprints and Sparse Volume Textures of the runtime profile's asset catalog (Prepare-ProjectAssets.ps1), or, without one, the staged runtime's levels and assets named with UE's prefixes for those types (SM_, SK_, BP_, SVT_). The delegate turns each such prim into a bounds mesh carrying the asset (a Mesh carries it itself; another prim gets a __HdUEAssetProxy child box, sized from the catalog's bounds, else 1 m), in every host alike: Houdini's viewport, husk and usdview render the same placements from the stage, which is not changed. Native assets retain their pivot, material slots, and centimeter dimensions. Authored and parent transforms follow stage units without double unit conversion.

A Sparse Volume Texture (a VDB imported in the UE editor) renders as UE's Heterogeneous Volume, with a dynamic instance of UE's SparseVolumeMaterial (/Game/HdUE/MI_HdUESparseVolume) bound to it, in both render modes. It keeps its VDB's transform, whose units UE reads as centimetres: a VDB written in metres needs a 100x scale on the prim. An animated SVT (a VDB sequence) shows the frame in primvars:unreal:volume:frame, UE's Heterogeneous Volume Frame, 0 for the sequence's first file (default 0). Key it over time as Sequencer keys Frame; there is no free-running playback, so a render is the same at any speed. A constant primvar, it can sit on the asset prim and reach the bounds proxy under it; Render Geometry Settings LOPs set it as Volume Frame (for example $F - 1). samples/conformance/volume/sparse_volume_texture.usda places the Cornell fog this way, sparse_volume_sequence.usda animates a two-file sequence.

Transform, visibility, deletion, and re-creation are supported. Level transforms reload the instance. Virtual-texture waiting also covers native materials. Skeletal meshes use reference poses; Blueprint game progression, time synchronization, and World Partition coverage remain limited.

Prepare-ProjectAssets.ps1 accepts explicit private content inputs and a required map. Keep all input projects, catalogs, generated scenes, and runtime profiles local and ignored.
