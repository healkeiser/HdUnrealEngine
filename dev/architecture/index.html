Architecture and runtime anatomy¶

This page describes what hdUE adds to a process, on which threads it runs and how one frame travels from Hydra to UE and back, so that each part can be checked in Process Explorer or a debugger. Statements come from the code (file names are given) or from live observation of husk and Houdini 22.0.368 on Windows 11 with an RTX 4090 and a 16-core Ryzen 9 5950X (October 2026, Cornell box). Anything that was not observed or read in the code is marked inferred.

Processes¶

hdUE runs entirely inside the host process. UE is linked into a DLL (UELibrary, unreal/HdUEBackend/Source/HdUEBackend.Target.cs: LinkType = Monolithic, bShouldCompileAsDLL = true, UE_LIBRARY_ENABLED=1), so there is no UE executable, editor or window.

Host Executable Who starts UE
Solaris viewport houdini.exe (and the other GUI names in houdiniUi(), src/hydra/delegate.cpp: houdinifx.exe, houdinicore.exe, hindie.exe, ...) The first hdUE delegate, once the Python host (hdue_houdini.py) has started because a Scene Viewer selected hdUE
husk, USD Render ROP husk.exe (the ROP launches it as a child of Houdini) The first hdUE delegate
hython hython.exe The first hdUE delegate (hython is not in the GUI list, so it gets the husk behaviour)
usdview python.exe running scripts/usdview_hdue.py The Python host itself (scripts/hdue_runtime.py, Runtime(start=True))

Child processes. During rendering hdUE starts none. A 10-frame Path Tracer and a 60-frame realtime husk render were polled every 500 ms for children: there were none. A Houdini session with hdUE in the viewport had one child, conhost.exe (Houdini's console). No ShaderCompileWorker runs: the runtime is a cooked game whose shaders come from ShaderArchive-*.ushaderbytecode in the staged Content folder, and the staged Engine\Binaries holds only ThirdParty (no ShaderCompileWorker.exe, CrashReportClient.exe or UnrealTraceServer.exe; UE logs "The Unreal Trace Server binary is not available").

The only child process hdUE can start is the background material preparation (Substrate Builder graphs, and MaterialX graphs the render-time translation cannot express; docs/substrate-builder.md, docs/materials.md), in Houdini's UI and in husk: when a material needs a prepared asset, scripts/live_materials.py starts pwsh (or powershell) with scripts/Prepare-LiveMaterials.ps1 (CREATE_NO_WINDOW, environment stripped of HOUDINI_*, PXR_*, QT_*, HDUE_RUNTIME_CONFIG, ...). That script runs standalone USD Python (Run-UsdPython.ps1) to write the job's graphs, one UnrealEditor-Cmd.exe for the HdUESubstrate commandlet (UE's MaterialX import, the Builder compile, then UE's cook), and the publish step. Its PID is written to runtime-state.json (material_preparation.worker_pid).

Why the hashed backend name. Update-HoudiniRuntime.ps1 copies the built HdUEBackend.dll to HdUEBackend-h22-<first 16 hex digits of its SHA-256>.dll beside it and writes that path into runtime-houdini.json. A running Houdini keeps its backend loaded until it exits (it is never freed), so a fixed name could not be replaced while Houdini runs, and a profile always names the exact binary it was made for (inferred from the script; the script itself states no reason). Several hashed copies accumulate in the folder; only the one in the profile is loaded.

Paths UE sees. Initialize starts UE with "<runtime_project>" /Game/HdUETest -game -windowed -d3d12 -unattended -nosplash -nosound -NoLoadingScreen -NoSplash -ResX=640 -ResY=360 plus Backend::boot's -RenderOffscreen, HDUE_UE_ARGS and -userdir="<HDUE_USER_DIR>" when set (HDUE_SHOW_WINDOW=1 drops -RenderOffscreen). UE's base directory is the backend's folder (LogInit: Base Directory: ...\HdUEBackend\Binaries\Win64/), and UE changes the process's working directory to it; the delegate restores the host's working directory after every tick (HdUESelfHost::tick), which husk needs for relative output paths.

Threads¶

Observed with a script that lists each thread's GetThreadDescription (UE names its threads with SetThreadDescription, WindowsPlatformProcess.cpp), its start address (NtQueryInformationThread(ThreadQuerySetWin32StartAddress)) mapped to a module, and its CPU time: the same columns as Process Explorer's Threads tab. hdUE itself names no thread.

Who owns UE¶

The backend accepts calls only from the thread that called initialize (Bridge.cpp, CheckOwner: HDUE_WRONG_THREAD otherwise; get_status, poll_frame, copy_frame, copy_depth, acquire_gpu_frame and AOV copies are readable from any thread). That thread is UE's game thread. Because it is not the thread that ran the DLL's static initialization, the target defines IS_RUNNING_GAMETHREAD_ON_EXTERNAL_THREAD=1.

In husk, hython and Houdini's UI, the owner is an std::thread that the first delegate creates (startSelfHost, HdUESelfHost::worker in delegate.cpp). It creates a hidden HdUESelfHost window (passed to UE as its window), loads the backend, calls Backend::boot and then serves a queue:

  • run(f) queues f and waits for its result; post(f) queues it without waiting. On the worker itself both run inline.
  • When the queue is empty, it ticks (PeekMessageW dispatch, api().tick(), restore the working directory). In Houdini's UI it ticks continuously, waiting at most 2 ms for work while any viewport delegate is not paused, and after each tick runs the render passes' "pumps", which publish finished frames without waiting for Houdini to call Execute. Under husk it only runs queued work; ticks happen inside Execute.

In Process Explorer this thread is GameThread with a start address in ucrtbase.dll (the CRT thread entry of std::thread), not in the backend. In the Houdini session it was thread 7436 while Houdini's UI thread (start address houdini.exe, unnamed) was 48420, the owner the Python host recorded in runtime-state.json; GameThread CPU time grew while the viewport rendered. The Python host (hdue_houdini.py) never ticks UE: its 16 ms QTimer (250 ms while no Scene Viewer renders with hdUE and no walk is pending) does housekeeping (materials, op: textures, asset overrides, status) and it attaches with Runtime(start=False). Its stage walks are cooperative jobs (scripts/cooperative.py): generators that yield between prims, which the timer advances for at most 8 ms (material preparation) and 4 ms (asset overrides and op: textures) per tick, never while Houdini cooks the viewed stage, so Houdini's UI thread is never held by one; a long walk shows its progress in Houdini's status bar. A walk starts only for a change it reads (_changes: shading prims, bindings, wet and Substrate opinions for materials; shader and light images for op: textures; asset prims, unreal:surface:* and instancing for overrides), never for a light, camera or transform edit, and a change during a walk starts the next one once it has applied its result. A walk that meets a prim an edit removed starts over on the new stage. husk and usdview run the same walks to completion (cooperative.run). On NVIDIA's Da Vinci Workshop (3,000 MaterialX materials, 6,700 meshes) the walks held Houdini's UI for about 2.5 of the 4.5 minutes it froze on selecting hdUE, and for 45 s on every light edit.

Work from other threads reaches the owner through ueRun (delegate.cpp): with the worker, run(f); without one, inline. hdue_run_on_ue_thread runs a task through the same path and returns when it has run; the attached Python host sends every backend call it makes through it (Runtime.on_ue_thread, scripts/hdue_runtime.py). Live Render creates the delegate on one thread and executes it on others, which this indirection covers. In usdview, hdue_runtime.Runtime(start=True) initializes and ticks UE on usdview's Python thread; the delegate finds UE READY and starts no thread.

hdUE's parallel work¶

  • Delegate (host side). Hydra syncs prims on its own TBB workers (HdRenderIndex::SyncAll); prims write into HdUEState under its mutex. prepareMeshes converts points, normals and UV sets with WorkParallelForN; HdUEToSceneLinear (OCIO) and the render buffers' copies (render_buffer.cpp) use it too. Colour textures in another colour space are converted once through OCIO into EXRs under %TEMP%\hdue_ocio.
  • Backend (UE side). ApplyScene builds static meshes with ParallelFor over the batch (Scene.cpp); texture block compression and readback conversion use ParallelFor. Interactive hosts launch Lumen card and Nanite builds as UE::Tasks at BackgroundLow priority (HdueConversion), one per set of identical meshes, which TickConversions swaps in on the game thread; a scene being destroyed waits for its running builds. Offline hosts build them inline before the frame.

One frame¶

  1. Sync (host thread, Hydra workers). Rprims (Mesh, Points, Curves, Volume in prims.cpp), sprims (materials, lights, cameras) and bprims (render buffers, fields) copy what UE needs into HdUEState: geometry, transforms, materials, and dirty sets (dirtyMeshes, movedMeshes, ...). Each change bumps revision. No UE call happens during Sync.
  2. Execute (Pass::_Execute, host thread). Copies the pass state (AOV bindings, buffers, view, projection, camera values) into a PassSnapshot, since Houdini reuses those objects once Execute returns. Then:
  3. husk / hython: host.run(...) blocks the host thread while the UE thread calls executeOnce repeatedly for up to 250 ms or until converged, so a realtime frame costs GPU time rather than husk's polling interval.
  4. Houdini's UI: host.post(...) and return at once; calls arriving while one is queued are coalesced to the newest camera, and the pump keeps publishing until IsConverged.
  5. executeOnce (UE thread). Ticks UE (unless the loop just did), creates or resizes the session (create_session, resize_session), and when revision changed: prepareScene takes the dirty sets under the state lock into a ScenePacket of ABI descriptors (a mesh that frees its arrays once uploaded moves them into the packet, released in the state, and convertDeferred builds its descriptor after the lock is released: built under it, a 1 GB streaming batch held the lock for 0.7 s while every Hydra Sync thread waited), then sendScene calls apply_scene (meshes, materials, removals; reset_scene on the first batch), then the lighting, volume, asset, surface and motion functions (set_transforms for moved meshes, keeping their geometry). Then it builds an HdueRenderRequest (UE centimetres, +X forward, +Z up; generation, mode, samples, warmup, projection, depth of field) and calls request_render when the request changed, then poll_frame / copy_frame (and copy_depth, poll_aov, copy_aov_buffer for AOVs).
  6. UE tick (Tick, Bridge.cpp). UELibrary_Tick, native assets, lighting and TickConversions; retire finished readbacks and poll the pending ones; when the Path Tracer's virtual texture warm-up is ready, reset the view state; unless the current request's frame is converged, Draw.
  7. Render. Draw builds a scene view family for the session's render target (SCS_FinalToneCurveHDR, so the float target gets UE's tone curve as linear Rec.709) and RenderAndReadBack calls BeginRenderingViewFamily. A frame converges after samples_per_pixel Path Tracer draws, or after warmup_frames full-resolution realtime draws; offline, the next frame of a sequence keeps the history and converges after one.
  8. Readback (CPU path). A FRHIGPUTextureReadback copies the colour (and depth, Path Tracer albedo/normal guides) in one of three slots. On a later tick the render thread locks it, converts half floats to float RGBA with straight alpha (and device depth to linear centimetres), and publishes Pixels and Frame under FrameMutex, with frame_id, generation, converged, completed_samples. poll_frame returns the newest frame; the delegate compares its generation with the request's so a stale frame is not shown as current.
  9. Shared GPU frames (Solaris viewport). With configure_gpu_frames enabled, each beauty draw is also written into a ring of three shared D3D12 textures (RGBA16F colour, R32F depth, bottom row first) and UE's queue signals a shared ready fence (SharedFrames.cpp). On the GL thread, HdUERenderBuffer::GetResource → HdUEGpuFrames::color calls acquire_gpu_frame, imports the NT handles once per ring (GL_EXT_memory_object_win32, GL_EXT_semaphore_win32), waits for the ready fence on the GPU (glWaitSemaphoreEXT), copies into HgiGL textures (glCopyImageSubData) and signals the release fence. The CPU readback then runs only for converged frames, and Houdini composites the CPU buffers once they hold the converged frame, since its selection highlight lines the CPU primId buffer up with a CPU colour buffer. Motion blur, the denoiser, a non-Rec.709 OCIO scene_linear, husk, usdview, Live Render and HDUE_GPU_FRAMES=0 keep the CPU path (docs/houdini/index.md).
  10. Publish (delegate). Pixels are converted to the OCIO scene_linear space when needed, written into the bound HdUERenderBuffers (colour, depth, AOVs, Cryptomatte), and the host maps them: husk writes the image, Houdini draws it.

Interactive and offline profiles¶

Backend::boot passes HDUE_INIT_INTERACTIVE exactly in Houdini's UI (houdiniUi()); every other host gets the offline profile.

Startup and shutdown¶

Startup. HdUnrealEngine::CreateRenderDelegate → HdUERenderDelegate constructor → hdue::Backend loads the backend and fills its one table from hdue_get_api (checked for version and size) → if no worker exists, get_status; when COLD, startSelfHost:

  • husk and hython wait for the boot; Houdini's UI returns at once (work posted meanwhile runs once UE is ready, and a boot failure is kept in bootError and reported by every later delegate).
  • On the new thread: hidden window, Backend::boot(instance, window, runtime_project, interactive) → Initialize: owner thread, embree/tbb preload, UELibrary_InitW, checks for GEngine, a non-null RHI and a game world with a scene, offline cvars, READY. Then std::atexit(shutdownSelfHost).

UE starts once per process. Later delegates (the next viewport, husk --restart-delegate) increment host.delegates and reuse it; deleting a delegate destroys its session (destroy_session releases the scene, readbacks and view states) but not UE. The backend has one session at a time ("The initial backend supports one active session."). Under husk, UE starts before husk prints >>> Render ... frame 1 (observed); about 3 s elapse between husk loading the stage and "Engine is initialized".

Shutdown in Houdini's UI. Host.close (Qt aboutToQuit, or atexit) calls hdue_shutdown_ue → shutdownSelfHost: on the UE thread, one tick, Backend::shutdown → Shutdown (DestroySession, UELibrary_Shutdown), destroy the window; then join the thread. Shutdown also constructs a function-local static whose destructor, which runs before UE's own static destructors at process exit, hands the game thread to the exiting thread (FTaskTagScope::SwapTag(ETaskTag::EGameThread), GGameThreadId = current thread), since ~FScheduler checks it runs on the game thread. Viewports that still draw afterwards report converged without rendering.

Shutdown elsewhere (husk). Nobody calls hdue_shutdown_ue. ExitProcess ends every other thread, including UE's, and then runs the DLL's atexit handlers at detach: shutdownSelfHost finds the worker thread already signalled and calls TerminateProcess with the exit code already set, because UE can no longer shut down from there and waiting for it hung the exit (delegate.cpp). So a husk process ends without UELibrary_Shutdown; observed exit code 0 for both renders. hdue_backend_smoke covers the clean path with UE on a worker thread through process exit.

Restart. Not possible: UELibrary cannot initialize again after Shutdown (Initialize returns HDUE_INVALID_STATE unless COLD), so a stopped UE stays stopped until the process exits.

Failures and where to look.

  • UE's log: <runtime project>\Saved\Logs\HdUEBackend.log, previous runs as HdUEBackend-backup-<time>.log, or under HDUE_USER_DIR (-userdir) when the package sets it. It holds every line. The host's stdout (husk's console, Houdini's Log Viewer, which shows the process's output under Standard Output) gets every Warning and Error line of every category (each warning once) and each PSO precache miss (Encountered a new ... PSO (PSOPrecacheState: Missed), which UE logs at Display but which is a PSO compiled on the render thread), as UTF-8. Other Display and Log lines are progress and stay in the file, as a UE game shows its user none of them. UE echoes every Display line by itself (FFeedbackContextAnsi, or -stdout), so Initialize swaps GWarn for UE's base FFeedbackContext when the output devices are created (FCoreDelegates::OnOutputDevicesInit) and adds a filtering device (FHdueConsoleEcho, Bridge.cpp); HDUE_UE_ARGS=-stdout restores UE's full echo.
  • husk shows no Tf warnings of a delegate, so hdUE prints its own to stderr as hdUE warning: ... (once per message) and frame failures as hdUE error: ..., and sets huskErrorStatus so husk exits non-zero.
  • Houdini's host: HDUE_HOUDINI_LOG_DIR, else $HOUDINI_TEMP_DIR/hdUE/<pid>/ (integration.log, runtime-state.json with the UI thread id, UE state, errors and the Substrate worker; ue.log is the name passed to the attached Runtime).
  • HDUE_TRACE_TIMING=1 (to HDUE_TRACE_FILE when set) prints slow ticks, slow tasks and where each Execute spent its time.
  • A UE crash is handled in process by UE's handler (CrashReportingThread); no crash reporter is staged, so none starts (inferred from the staged files). A hang in Houdini's UI shows the UI thread waiting in HdUESelfHost::run (a std::future::get: render stats, delegate and render pass destruction still use run) while GameThread is busy or blocked; Execute itself only posts.

Memory, GPU and disk¶

  • Scene data exists twice. The delegate keeps its own copy in HdUEState (points, normals, UVs, indices, transforms, materials) so that later edits resend only what changed; HDUE_TRACE_SCENE prints its running size during sync. submit sends it in batches of about 1 GB of stored geometry: each batch's ScenePacket holds its converted descriptors for the duration of apply_scene, which copies everything it needs (strings included) before returning (one packet for a whole scene copied it all a second time). Mesh rprims keep nothing of their own: the wet-mask refresh triangulates from the scene delegate when it needs a mask. Change detection compares a hash of each mesh's arrays (HdUEGeometryHash). Nor is the copy kept once UE has the mesh: once UE has a static mesh, finishScene frees its arrays (deforming, wet, masked and displaced meshes keep them). A later material, visibility or sidedness change reaches UE through update_meshes (C ABI 13) without the geometry, and a move through set_transforms; Sync compares the re-read arrays with the stored hash and frees them again. When UE needs the geometry after all (needs_upload: a static mesh made editable, or a Nanite mesh given a translucent material), the render pass calls the rprim's Sync itself with the geometry bits (HdUERepullMeshes), as Hydra would for a dirty prim (Houdini's viewport never syncs an rprim the render pass marks dirty), and frames do not converge until it is back. A mesh made wet after its upload comes back this way, and uploads dynamic. Large scenes are uploaded while Hydra still syncs them (HdUEStreamMeshes, husk, hython and Houdini's viewport): once 1 GB of stored geometry waits, hdUE's UE thread uploads it in batches (creating the session at the render settings' resolution if the first Execute has not come yet), and Sync threads wait while more than 4 GB waits; HDUE_STREAM_BYTES sets the batch size for tests. usdview keeps its copy, which its CPU ray picks read; Houdini's viewport picks from the ID AOVs UE renders and needs none. UE then owns its meshes (UStaticMesh render data without CPU copies once on the GPU, as UE's runtime builds, Nanite data, Lumen cards, dynamic meshes), materials, lights and textures in its world. Observed working sets: 2.7-2.9 GB for husk on the Cornell box, 5.1 GB for the Houdini session.
  • Heavy scenes. NVIDIA's Da Vinci Workshop shot (6,700 meshes, 617M triangles, render purpose) in Houdini's viewport (Launch-Houdini.ps1 -TestKind heavy, under a job memory limit with a commit timeline): before the changes below, the process ended at a 24 GB limit 67 s in, after 4 of its uploads, with "Out of video memory": the interactive first-pass meshes were full-resolution static meshes, and Windows charges a process's D3D12 allocations to its commit (all of them would have needed about 110 GB, 200 bytes per vertex). Now first passes stop at an estimated 2 GB (r.HdUE.InteractiveFirstPassMemory), the other meshes appear as their Nanite builds swap in, and the copies of a mesh in later uploads reuse its first pass. The shot then converges in 180 to 210 s with a job peak of 30 to 33 GB (one build per distinct mesh, 1,700, from a warm Nanite cache), and through its camera 3 s later. Of 22.5 GB during the upload, UE's LLM tracked 10.5 GB (8.6 GB of heap, most of it the copies of meshes whose builds wait for memory, and 2.4 GB of graphics); Houdini, its USD stage and the delegate held the rest. A Houdini session showing a small stage through hdUE holds about 10 GB. Houdini recreates its renderer once after the first frame of this stage (HUSD_Imaging::setupRenderer calls resetImagingEngine when its restart check, updateRestartCameraSettings or anyRestartRenderSettingsChanged, is true; read from libHUSD.dll's exports). It happens with the proxy purpose, without the scene camera, with viewport lighting off (no work light), with empty or dummy restartrendersettings and restartcamerasettings in UsdRenderers.json, with the stage's frame rate matched, and without hdUE's host steps (material, texture and asset sync). It does not happen on either half of the stage, on Cornell, smoke.usda or selection.usda. Just before it, Houdini's second evaluation of the render settings reaches the delegate (houdini:fps 24 to 60, shutter:open/close 0 to -0.25/0.25), which on small stages arrives without a reset. Nothing hdUE sends was found to trigger it, which syncs the stage again: destroy_session now frees the old scene at once with UE's UEngine::TrimMemory, as UE frees a level before loading the next, where it stayed until UE's next periodic garbage collection and the second sync passed 40 GB. Inside a Windows job with a memory limit, UE's available memory is the job's (memory.WindowsPlatformMemoryUseContainerMemory), which the background builds are scheduled against. Under husk, with streaming and freed copies, it got through the upload until UE's limits: Nanite's root page pool (one GPU buffer of at most 2 GB on NVIDIA, less 512 MB of streaming pool, holds about 100M of its triangles, since every page of a runtime mesh is a root page) and then the GPU memory of the meshes left without Nanite. Runtime meshes now keep one root page each and stream the rest from memory (an engine edit, Apply-ResidencyPatch.ps1; UE streams only cooked files outside the editor), so the root pool no longer bounds it. Three more things held host memory, each found with a job memory limit, a timeline of the process's commit and a map of its committed regions (VirtualQueryEx): the arrays of released meshes, which v = {} cleared without freeing (assign of an empty list keeps the capacity: about 30 GB in Houdini's mimalloc); Windows charges the process a commit for its D3D12 allocations, and each Nanite mesh kept a full-resolution LOD 0 and ray-tracing BLAS (about 200 bytes per triangle, write-combined regions as large as the GPU's dedicated and shared use), now the Nanite fallback as in UE's static mesh build; and 5,000 of its 6,750 meshes are copies of 1,700, which now share one static mesh each, as UE's USD importer shares them. Reading every render-purpose mesh through USD alone holds 1 GB. Under husk the shot now renders with a job memory peak of 22 GB (it ended at 32 to 38 GB limits before): 656 s from an empty Nanite cache, 117 s from it. Its first frame then hit a UE 5.8.4 bug, a Nanite raster pass that left its read-only dummy buffer in the renderer for Lumen's next card-capture pass to write (DXGI_ERROR_INVALID_CALL), fixed by an engine edit (Apply-ResidencyPatch.ps1). The proxy purpose (Houdini's display options) renders it in about 9 GB.
  • GPU. One render target per session, three readback slots (colour, depth, Path Tracer guides), the AOV view state when AOVs are requested, and, in the Solaris viewport, the three-slot shared ring (colour and depth textures, a ready and a release fence) that GL imports. acquire_gpu_frame returns new NT handles when the ring changes (first call, resize, depth toggled), and the caller closes them.
  • CPU frame buffers. The backend keeps the newest beauty frame, depth, guides and AOV pixels as float arrays under FrameMutex, recycled through spare buffers; copy_frame copies into the caller's buffer. The delegate's render buffers hold their own copy for Map().
  • On disk.
  • Shaders: the cooked shader archives in <runtime>\HdUEBackend\Content and GlobalShaderCache-PCD3D_SM6.bin; nothing is compiled at run time.
  • PSOs: none bundled (docs/building.md, "PSOs"). UE's own PSO disk cache is off (r.D3D12.PSO.DiskCache=0 in the log); the NVIDIA driver keeps its own shader cache (inferred).
  • Converted OCIO textures: %TEMP%\hdue_ocio, entries unused for a week removed (color_management.h).
  • Nanite builds: Saved\NaniteCache (BuildNanite, Scene.cpp), keyed by the builder's version and the mesh's content, entries unused for a week removed.
  • Block-compressed textures: %LOCALAPPDATA%\hdUE\TextureCache (CachePath, Scene.cpp), entries unused for a week removed.
  • Virtual textures: %LOCALAPPDATA%\hdUE\VirtualTextureCache (VirtualTextureBuild.cpp), manifests unused for a week removed with the chunks no other manifest names (a day's grace for chunks a running build has not named yet).
  • UE's Saved (Logs, Config, NaniteCache): %LOCALAPPDATA%\hdUE\Saved, where an installed UE game keeps it (UserSettingsDir(), FPaths::ProjectUserDir), or under HDUE_USER_DIR (-userdir, src/client/backend.cpp).
  • Houdini's host: its log directory (above) and exported op: texture images, removed on shutdown (docs/houdini/index.md).

ABI¶

include/hdue/bridge.h is the whole backend ABI: HDUE_ABI_VERSION 24, engine 5.8.4. The backend exports one function, hdue_get_api(version, capacity, &api), which fills HdueApi (368 bytes: struct_size, abi_version and 45 function pointers) for exactly HDUE_ABI_VERSION, or returns HDUE_ABI_MISMATCH (another version) or HDUE_BUFFER_TOO_SMALL (capacity under sizeof(HdueApi)) without touching the table. src/client/backend.cpp and scripts/hdue_runtime.py load it once and check its version and size. It does not start UE, and the DLL must stay loaded until process exit. Fixed-width POD fields, UTF-8 strings copied during the call, opaque handles and caller-owned buffers cross it; UE, USD and STL types, exceptions and memory ownership do not. The delegate and backend come from the same build, so there are no optional parts: a change to any function or descriptor bumps the one version.

Motion blur¶

UE's Path Tracer has no motion blur of its own (Movie Render Queue averages sub-frames). hdUE does the same inside the delegate: rprims record their transform samples one frame either side (SampleTransform, SampleInstancerTransform) and their velocities; the camera sprim records its own. When the render camera has an open shutter and something moves, the render pass renders unreal:motionSamples sub-frames at times spread over [shutter:open, shutter:close], moving meshes through set_transforms (which leaves geometry untouched), and publishes the running average. Instances with time-sampled positions, orientations, scales or matrices (and no velocities) are evaluated at each sub-frame from the instance matrices at every sample time in the window, interpolated as UsdGeomPointInstancer::ComputeInstanceTransformsAtTime interpolates the primvars (positions and scales linearly, orientations by slerp; HdUEInterpolateInstance). Deforming meshes, and the companion mesh into which a generic prototype's sheared instances are baked (a mesh of its own, split off at Sync: HdUEStoreShearCompanion), are re-uploaded per sub-frame; the prototype's other instances only move. Path Tracer samples are divided between sub-frames. AOVs render the unblurred pose at the current time.

Inspecting a process¶

The thread table above came from this PowerShell, run against a husk or Houdini PID while it renders (THREAD_QUERY_INFORMATION is needed: GetThreadDescription returns access denied with the limited right):

Add-Type @"
using System; using System.Runtime.InteropServices;
public static class Th {
  [DllImport("kernel32")] static extern IntPtr OpenThread(uint a, bool i, uint id);
  [DllImport("kernel32")] static extern bool CloseHandle(IntPtr h);
  [DllImport("kernel32")] static extern int GetThreadDescription(IntPtr h, out IntPtr d);
  [DllImport("ntdll")] static extern int NtQueryInformationThread(IntPtr h, int c, out IntPtr v, int l, IntPtr r);
  public static string Name(uint id, out long start) {
    IntPtr h = OpenThread(0x40, false, id), p, v; start = 0; string s = "";
    if (h == IntPtr.Zero) return "?";
    if (GetThreadDescription(h, out p) >= 0 && p != IntPtr.Zero) s = Marshal.PtrToStringUni(p);
    if (NtQueryInformationThread(h, 9, out v, IntPtr.Size, IntPtr.Zero) == 0) start = v.ToInt64();
    CloseHandle(h); return s;
  }
}
"@
$p = Get-Process -Id <pid>
$p.Modules | Select ModuleName, FileName
$p.Threads | % { $s = 0L; $n = [Th]::Name([uint32]$_.Id, [ref]$s)
  $m = $p.Modules | ? { $s -ge $_.BaseAddress.ToInt64() -and $s -lt $_.BaseAddress.ToInt64() + $_.ModuleMemorySize }
  "{0}`t{1}`t{2}`t{3}" -f $_.Id, $n, $m.ModuleName, $_.TotalProcessorTime }
